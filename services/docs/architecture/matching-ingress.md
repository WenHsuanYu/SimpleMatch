# Matching ingress and recovery boundary

The target Matching runtime has 15 fixed instances. StatefulSet ordinal N owns
`matching.commands` partition N and publishes to `matching.events` partition N. Kubernetes
configuration supplies the ordinal/partition, but the native domain boundary accepts only a valid
`PartitionOwnershipPermit`; it does not depend on Kubernetes API types.

Before polling, replaying, or publishing, a pod must:

1. load and validate the final daily Market Reference Artifact;
2. acquire its partition Lease and obtain an ownership permit;
3. locate and replay the retained Open Barrier for the same trading session; and
4. catch up to an acceptable contiguous Kafka watermark before becoming Ready.

The pod self-fences ingress, the single-writer core, and the publisher when Lease renewal cannot be
confirmed for five seconds. A replacement must wait for ownership, replay the same ordered command
stream, and reach the accepted lag/readiness gate. Commands and cancellations remain retained in
Kafka while that partition is unavailable; they are never rerouted to another Matching instance.

## Hot-path shape

Kafka ingress decodes and validates each command before offering it to a preallocated SPSC input
ring. One pinned single-writer core owns all order books for the partition and writes deterministic
results to a preallocated output ring. Network, disk, PostgreSQL, Kubernetes, Kafka commits, and
post-warmup allocation remain outside the core.

The publisher uses idempotent production with `acks=all`. It tracks every output generated by an
input command. An input offset becomes completed only after all its outputs are acknowledged, and
the offset coordinator commits only the highest contiguous completed offset. A crash after output
acknowledgement but before input commit therefore replays the command and may republish byte-
identical events; downstream durable inboxes suppress the duplicate business effect.

## Current implementation seam

The repository currently has only tested routing/quarantine ingress state machines and CMake
scaffolding. They are reusable characterization evidence, not the final runtime interface. The
Kafka client, rings, order books, deterministic matching core, barriers, publisher, offset
coordinator, ownership permit adapter, and recovery certification remain open work in the
[remaining-work inventory](../../../docs/routing-policy-remaining-work.md).
