# Category E necessity assessment

Category E reduces the custom deployment and recovery checks after category C.
The decision starts with the failure each check protects.
A change in language percentage is not evidence of lower maintenance cost.
The owner authorized one complete E batch and one local commit after category C.

## Final responsibility decisions

| Responsibility | Decision | Necessary behavior |
| --- | --- | --- |
| Dependency report evaluation | Migrate the complete predicate and its tests to Java. | Preserve distinct PostgreSQL, Redis, and Kafka recovery claims. |
| Placement and serving evaluation | Migrate snapshots, health data, linked-file checks, and report construction to Java. | Prove placement, immutable image identity, stable Pods, and service health across a sufficient Redis outage. |
| Connect task and report evaluation | Replace the custom Ruby evaluator with Java. | Link the exact deleted task owner to reassignment and a new Account event after the baseline. |
| Live fault operations | Keep existing commands and their behavior tests. | Enforce ownership, current runtime preflight, exact deletion, bounded recovery, and restoration before PASSED. |
| Placement HTTP adapter | Keep a small Bash adapter and independent authenticated HTTP tests. | Use approved operations credentials for Freshness and anonymous health probes. |
| Production-like input creation | Keep the direct command test. | Create an immutable FIX dictionary and stop later inputs after failure. |
| Sensitive-log rejection | Keep independent FIX, secret, token, private-key, and Bearer cases. | Prevent the observer from retaining sensitive output. |
| Phase 1 collection | Keep one existing collection. | Execute each selected test once and propagate failures. |
| Two archived source-check suites | Delete both suites after preserving necessary command behavior. | API failure prevents pruning, manager refusal prevents fallback deletion, and publisher failure preserves the previous lock. |

Java uses the existing Jackson and JUnit dependencies in `tools/recovery-evidence-verifier`.
This batch adds no library type, Spring context, shell entry point, planner, or generic fault framework.
The existing commands remain the operational interfaces.

## Retained data rules

Dependency evaluation preserves supported identity, fault mode, successful status, and component-specific recovery facts.
PostgreSQL retains its node-local volume and durable marker.
Redis remains disposable and moves away from a stopped worker.
Kafka retains its three broker and storage identities, restores ISR, preserves its marker, and observes catch-up.

Placement evaluation compares raw observations across baseline, outage, and restoration.
It checks two Ready Pods, distinct eligible nodes, one immutable image, stable Pod identities, and unchanged restart counts.
Health and serving responses must satisfy the same rules during capture and final evaluation.
The minimum outage follows the live liveness probe window. Changed timing cannot silently shorten the observation.

Connect preflight checks the two workers, PostgreSQL, Account and Risk migrations, owned connector tables, and internal Kafka topics.
The final evaluator checks task-owner identity, deletion evidence, reassignment, temporal order, and baseline-aware publication linkage.
A new owner Pod on the same node is valid.
The shared CDC validator retains exact payload, key, timestamp, and header checks.
Java does not duplicate those byte validators.

Namespace ownership, retained-runtime identity, current verifier execution, and executable node images remain preflight requirements.
The report does not repeat those checks through copied hashes or exact English success sentences.
Cleanup and tunnel closure must succeed before PASSED publication.

## Removed responsibilities

- Exact claim prose and redundant summary views in acceptance predicates.
- Unused envelope, status, and reason reader interfaces.
- Final-report revalidation of the full prerequisite and retained-authority chain.
- PDB, NoExecute timing, and unrelated service migrations for the direct Connect Pod-deletion scenario.
- Same-name replacement fixtures that cannot satisfy the actual reassignment loop.
- The single-adapter Connect phase callback and tests of its phase-name list.
- Archived assertions about function names, source spelling, syntax repetition, source line counts, and statement order.
- Duplicate suite calls and the separate static resilience result envelope.

The necessary replacements observe actual interfaces.
The Connect CLI tests use external-command doubles and execute the real preflight, scenario, shared CDC validation, and Java evaluator.
They cover success, UID drift, delete failure, unexpected deletion output, and cleanup failure.
Cleanup tests execute the real entry points and managers through isolated commands.
Publisher tests reach push failure and missing-digest failure with an existing valid lock.

## Schema and evidence scope

Dependency reports use schema version 2. Placement and Connect reports use schema version 3.
Keep older reports with their original source and date. Do not relabel them as current evidence.

Java tests check file semantics and command exit status.
HTTP fixtures check credential selection and request deadlines.
Command fixtures check operational failure propagation and cleanup.
These results do not establish deployed recovery or a new full-local certification PASS.

## Completion criteria

- Every E item has an explicit migration, deletion, or retention decision.
- Current callers, producers, source signatures, directory-based CI filters, and documentation agree.
- The complete Java suite, repository static analysis, and complete Lifecycle contract collection pass on the final source.
- Independent Standards and Spec reviews have no unresolved actionable finding.
- One local E commit follows category C. Unrelated worktree changes remain intact.

Count implementation, tests, and fixture data separately when reporting physical changes.
Include added Java and test helpers. Shell percentage alone is not the acceptance criterion.
